## 3. 映射公式与六道处理

```
joint = clamp_robot_limit(
            clamp_max_delta(
                neutral[joint]
                + sign * scale * Δangle(human → neutral)
                + offset
            )
        )
其中 Δangle 经过**周期归一化**（见 §5）
```

| 处理 | 作用 | 缺失后果 |
|---|---|---|
| 标定 neutral | 消除「人站在哪、初始什么姿势」的影响 | 换个人/换个位置就全错 |
| 相对角度 | 只映射变化量 | 绝对值受构图影响，不可复现 |
| **周期归一化** | 角度是周期量 | 170°↔−170° 会算成 340°，机械臂反向猛冲 |
| scale | 人机幅度匹配 | 人轻微动，机械臂甩到底 |
| offset | 微调中位 | 标定姿态下机械臂不在想要的位置 |
| max_delta | 人体大动作保护 | 人快速大摆臂会把机械臂甩出去 |
| 死区 + EMA | 抑制关键点抖动 | 机械臂高频抖动（阶段五会强化）|
| 机械臂限位 | 最后一道保险 | 可能撞限位 |

## 5. 过程中发现并修复的问题

### 5.1 【重要，已修复】角度周期归一化的陷阱

角度是周期量。若不做归一化，`170°` 与 `−170°` 的差会被算成 `340°`，
机械臂会朝相反方向猛冲并被 `max_delta` 顶到极限。

实现用 `angle_delta_deg()` 把差值归一化到 `(−180, 180]`。
有两个测试专门守住：
- `test_wraparound_does_not_fling`
- `test_angle_normalization_is_used`（验证 `1000°` 等价于 `−80°`）

**我自己的测试一开始写错了**：用 `1000°` 当输入并期望朴素差值 `+1000`，
实际代码给出的是 `−80°`（1000 mod 360 = 280 ≡ −80）—— **代码是对的，测试是错的**。
这件事记录在此，因为「周期量」这个坑很容易在后续阶段再次踩到。

### 5.2 【已修复】测试间配置污染导致误判

`cfg` fixture 原本是 `module` scope，而映射测试会就地修改
`cfg.filter.enabled`。前一个测试关掉滤波后，后续测试拿到的也是关的，
导致 6 个断言全部错位（曾表现为「joint2 目标恒为 0」）。

改为函数级 fixture 后正常。**教训：凡是被测试就地修改的配置对象，
都不能跨测试共享。**

### 5.3 【已修复】死区导致无法精确回到中立位

实测「回中立」停在 `0.907` 而不是 `0.900`：
死区（0.01 rad）把最后一步吞掉了，残留约 0.007 rad（0.4°）。

这是**设计取舍而非缺陷**（见 §7 已量化），但需要知晓：
死区越大，亚死区范围内的指令越无法精确到达。

### 5.4 【已修复】日志被 stdout 缓冲吞掉

`nohup` 重定向到文件时 stdout 变块缓冲（约 4KB 才刷一次），
日志文件长时间为空 —— **实际妨碍了排查**。
已在 `main()` 中显式 `sys.stdout.reconfigure(line_buffering=True)`，
并给每帧统计加 `flush=True`。

### 5.5 【已修复】启动脚本未清理占用摄像头的进程

首次重启时 `[FAIL] 无法打开帧源`：旧 demo 进程仍占用 `/dev/video0`。
已修正启动脚本：同时清理 perception 与 retargeting 两路进程，
并**等待真正退出**后再启动（`kill` 是异步的）。

## 8. 本次修正的映射参数（重要）

初版 sign 是**凭直觉写**的，实测后必须修正：

| 映射 | 初版 sign | **修正后** | 依据 |
|---|---|---|---|
| j2 | +1 | **−1** | joint2 正增量使腕下降，而人体上臂角向上为正，方向相反 |
| j3 | −1 | **+1** | joint3 正增量使前臂上抬，而人体「弯肘」是前臂下折 |
| j5 | +1 | **−1** | 实测 d(腕角)/dq = −2.7（量级小，依据较弱，可自行翻）|

### 8.1 顺带发现：neutral 必须留双向行程

改完 sign 后测试立刻暴露一个问题：

```
joint2 限位 [0, 3.14]，neutral = 0.9，sign = -1
人抬臂 -> joint2 减小 -> clip(0.9 - 1.2) = clip(-0.3) = 0.0   ← 撞下限
```

**表现**：机械臂抬到某个角度就不动了（单边饱和）。

这不是代码缺陷，而是**配置问题**，但不加约束会反复踩，
因此：
- neutral 由 `0.9` 调整为 **`1.3`**，使 joint2 上下行程均为 1.2 rad；
- 新增测试 `test_neutral_leaves_headroom_both_directions` 固化这条规则。

调整后各关节行程：

| 关节 | neutral | 上行程 | 下行程 | max_delta |
|---|---|---|---|---|
| joint2 | +1.300 | 1.200 | 1.200 | 1.2 |
| joint3 | −0.900 | 0.900 | 1.500 | 1.5 |
| joint5 | +0.000 | 0.800 | 0.800 | 0.8 |

### 8.2 测试不再写死参数

原先测试里写死了 `0.9` 等 neutral 值，一改配置就有 6 个测试失败。
现已全部改为从配置读取（`cfg.neutral_for("joint2")`），
**以后调参不会再改坏测试**。

---


当前配置的 scale 是**安全起步值**，需要实测后调整：

| 映射 | scale | 人在该量上的可用范围 | 机械臂行程 | 结论 |
|---|---|---|---|---|
| j2 | 0.020 rad/° | 约 ±90°（抬臂） | ±1.8 rad | 受限幅 1.2 rad，够用 |
| j3 | 0.015 rad/° | 0~150°（弯肘） | 0~2.25 rad | 受限幅 1.5 rad，够用 |
| **j5** | 0.012 rad/° | 约 ±60°（前臂转向） | ±0.72 rad | **偏小**，J5 行程 ±1.22 未被充分利用 |

**建议调参顺序**（配置注释里也写了）：
1. 先看 `sign` 对不对（人抬臂 → 机械臂是否上抬）；
2. 再调 `scale` 让幅度合适；
3. 最后调 `offset` 微调中位。

调参不需要改代码，只改 `config/retargeting.yaml` 后重启即可。

## 9. 新增行为：当前位姿作为初始位姿 + 丢失手臂自动平滑回位

### 9.1 需求与设计要点

需求：
1. 把「当前位姿」作为初始位姿；
2. 识别不到手臂时，**平滑**回到初始位姿。

**关键设计判断（容易做错的地方）**：
这里有**两个必须成对**的量，不能只设其中一个：

| 量 | 含义 | 作用 |
|---|---|---|
| 人的中立角度 `human_neutral` | 标定得到的人体基准角度 | 相对角度零点 |
| 机械臂初始位姿 `initial_pose` | 上位机下发的机械臂基准 | 映射绝对位置基准 |

两者必须对应**同一时刻**的「人-机」状态。否则映射零点错位，
人一动机械臂就从错误位置出发。
因此 `set_initial_pose()` **默认同时更新 `neutral_joints`**，并用测试守住。

### 9.2 丢失处理三段式

```
手臂丢失
  ├─ 宽限期内 (默认 1.0s)  -> 保持不动（给个明确状态）
  ├─ 超过宽限期           -> 关节目标以 return_home_speed 逐步逼近初始位姿
  └─ 重新识别             -> 把「人的基准」重置为当前姿势，避免跳变
```

**为什么要有宽限期**：人手一晃、被身体挡一下都会造成单帧丢失，
若立刻回位，机械臂会一惊一乍。

**为什么重新识别要重置基准**：人离开时机械臂回了初始位姿；
若延用旧基准，人回来后机械臂会从初始位姿**猛跳**回旧映射点。
重置基准后相对角为 0，机械臂平稳停在初始位姿附近。

**为什么是「平滑」**：回位只是「目标以比例速率推进」，
实际运动速度仍由 `piper_human_control` 的速率限制执行，所以不会跳变。

### 9.3 配置项

```yaml
robot:
  use_current_as_initial: true      # 启动时把当前实际位姿记为初始位姿
  initial_pose: [0.0, 0.6, -0.6, 0.0, 0.0, 0.0]   # 上面为 false 时使用
safety:
  return_home_when_lost: true       # false = 退回「保持不动」
  lost_grace_seconds: 1.0           # 连续丢失多久才触发回位
  return_home_speed: 0.6            # 每秒朝初始位姿推进的比例
  resume_on_reacquire: true         # 重新识别是否立即恢复映射
```

### 9.4 端到端验证结果

```

2) 正常映射：人上臂角 -60°  ->  J2 = 1.7813
3) 丢失（超过宽限期后）    ->  已回到初始位姿
```

### 9.5 过程中发现并修复的两个真实缺陷

**① 丢失计时少算一个控制周期**
初版把 `_lost_since` 设为「当前帧时刻」，导致丢失第一帧
`lost_for = now - now = 0`，宽限期被凭空拉长一个周期。
30Hz 下只多 33ms 不易察觉，但**帧率低或程序有卡顿时**
会出现「手臂已经丢了却还不动」的可感延迟。
已改为用**上一帧时间戳**作起点，并加回归测试。

**② 时间基准变化会让回位功能永久失效**
`now` 必须是绝对值（`time.monotonic()`）。若调用方误传相对时间，
`_last_update_time` 会远大于 `now`，`lost_for` 算出巨大负数
（实测 **−724639s**），宽限期永远不满足 -> **回位功能永久不触发**。
已加入时间倒退检测与自愈，并加回归测试。

> 这两个缺陷都是靠**端到端测试**（而非单元测试）暴露的：

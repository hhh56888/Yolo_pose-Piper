## 一、当前映射

```
Human Upper Arm  →  J2   (肩部抬起/放下)
Human Elbow      →  J3   (肘部屈伸)   ← 2D 下最可靠的量
Human Forearm    →  J5   (腕部屈伸)
Hand.openness    →  Gripper (joint7/joint8)   [接口已实现，mode 可选]
J1 / J4 / J6     →  固定安全值（2D 无法可靠观测这三个自由度）
```

### 为什么不是一一对应

```
✗  人体肩膀 = Piper J1
✗  robot_joint = human_angle
```

人体与 Piper 的运动学结构不同（连杆长度、关节零位、关节顺序），
且人体**绝对角度**受摄像头安装角度、人的站位/身高/初始姿势严重影响。
因此本方案：

1. 先做初始姿态标定，得到人体基准角 `human_neutral`
2. 只映射**相对角度** `Δ = human_angle − human_neutral`
3. 用区间归一化公式映射到关节行程

### 映射公式（唯一入口 `map_human_to_robot()`）

```python
delta = human_angle - human_neutral                      # 相对角(度)
ratio = (delta - human_min) / (human_max - human_min)    # 归一化
ratio = clamp(ratio, 0, 1)                               # clamp=true 时
robot = robot_min + ratio * (robot_max - robot_min)
if invert: robot = robot_min + robot_max - robot       # 方向统一在此处理
robot = robot + offset
robot = clamp(robot, 关节真实限位)                        # 最后一道保险
```

**方向翻转全部由 `invert` 完成，主程序里没有任何 `angle = -angle`。**

### ⚠️ 新增的硬约束（启动即校验）

```
human 区间必须相对 Δ=0 对称，且 (robot_min+robot_max)/2 必须 = neutral
```

**原因**：标定姿势对应 Δ=0，此时机械臂应停在中立位姿。
若不对称，Δ=0 会落在 ratio≠0.5，机械臂一启动就偏位。
实测踩过：`human=[20,150]`（中点 85）而标定基准在 90，
Δ=0 时 ratio=−0.15 被 clamp 到 0，关节直接跑到区间端点。

现已由 `RetargetingConfig.validate()` **启动即报错**并给出修复提示。

## 六、过程中发现并修复的缺陷（按发现顺序）

优化过程中修复了 **12 个真实缺陷**：前 6 个在编码与单元测试阶段发现
（其中 3 个是本次引入、3 个是原架构遗留），
后 6 个**只有真跑起来才会暴露**（缺陷⑦~⑫，见第八节）。
全部是「先找根因」而非硬编码绕过。

### ① `max_step_rad` 粗限幅破坏了滤波（本次引入）

**现象**：设关节目标 1.55，实际输出 0.7。

**根因**：粗限幅放在「映射之后、关节滤波之前」，
滤波器算出的值又被截断一次。最终输出由「alpha 与限幅谁先谁后」
决定，**调 alpha 的效果被限幅掩盖**。
而真正的速度/加速度限制已在 `SafetyLimiter` 里按
`min(a·dt, v·dt)` 每关节独立正确实现 —— 这一层纯属多余且有害。

**修复**：移除该限幅，并删除配置项，在 YAML 里写明「限速在哪一层做」。

### ② 标定锚点与映射区间不一致（本次引入）

**现象**：Δ=0（人保持标定姿势）时机械臂不在中立位姿。

**根因**：`human=[20,150]` 中点 85° ≠ 标定基准 90°，
Δ=0 落在 ratio=−0.15，被 clamp 到 0 → 关节跑到区间端点。

**修复**：把区间改成相对 Δ=0 对称、且 robot 中点 = neutral；
并加入**启动即校验**，同类错误再犯会直接报错并给出修复提示。

### ③ `invert` 方向错误（原架构遗留）

**现象**：J3 方向反了 —— 人伸直肘时机械臂反而更弯。

**根因**：初版 `invert` 是凭直觉写的，没有把
「人体角度增大的物理含义」与「关节正增量使腕往哪走」对上。

**修复**：不再靠推导，而是**用 TF 正运动学实测**：
```
只改一个关节，读 link6 相对 base_link 的 z：
  q3 −1.10 → z 0.5215
  q3 −0.85 → z 0.4478
  q3 −0.35 → z 0.2802
  q3 −0.10 → z 0.1970
=> q3 增大 → 腕上升（严格单调）
```
据此反解出正确 `invert`，并把实测数据写成测试里的 `DZ_DQ` 表，
**以后改配置若方向弄反，测试立刻失败**。

### ④ 控制循环无显式限频（原架构遗留）

**根因**：控制周期由推理耗时决定。YOLO 首帧 1.1s 或偶发卡顿
会直接表现为控制周期拉长。虽有 `dt` 夹紧保护，
但「控制频率不确定」本身不该出现在实时遥操作里。

**修复**：控制循环显式限频（`control_hz=30`），并把**感知放到独立线程**，
控制循环按固定周期取「最新一帧」结果。即使推理卡顿，控制周期仍稳定。

### ⑤ `gripper.py` 顶层 import rclpy（本次引入）

**根因**：导致 `piper_human_control` 在没有 ROS2 的机器上无法导入，
破坏了「配置类可脱机单测」的设计。

**修复**：改为惰性导入（与既有 `controller`/`streaming` 同一套模式）。

### ⑥ 验证脚本自身的激励构造错误（本次引入，连环 3 个）

这是**最有教育意义**的一处，因为它伪装成「映射不工作」：

| # | 错误 | 表现 | 根因 |
|---|---|---|---|
| 6a | 每阶段用「当前位姿」当锚点 | j3 逐阶段漂移到 −2.795 贴限位后不再动 | 锚点必须是可复现的居中位姿 |
| 6b | 激励把上臂/前臂转同方向 | 肘夹角 0°（伸直）而非弯曲 | 肘夹角 = 前臂角 − 上臂角 |
| 6c | 把「绝对肘夹角」填错位置 | 得到 40° 而非 130° | 需 `fore = upper + 肘夹角` |

**教训**：验证脚本本身也要先自证正确。
一个错的激励会让正确的映射看起来像坏的 —— 我一度据此怀疑映射逻辑，
直到单独打印内部量（`raw_elbow=40` 而期望 130）才定位到是激励写错。

## 八、实机运行验证（代码写完 ≠ 能跑）

单元测试只能证明「逻辑自洽」，证明不了「跑起来对」。
本节记录**真实跑起来之后**才暴露的六个缺陷（⑦~⑫），以及修复后的实测数据。

### 8.1 缺陷⑦：打开可视化窗口会把 30Hz 控制循环压到 4.2Hz

**发现方式**：对照实验（同一段 300 帧录像，只切换是否开窗口）。

| 运行模式 | 环路耗时(均/峰) | 超时次数 | 真实控制频率 |
|---|---|---|---|
| **有显示窗口** | **218.3 / 282.8 ms** | **268 / 268（100%）** | **4.2 Hz** |
| `--no-display` | 0.5 / 1.5 ms | 0 | 30.0 Hz |

**根因**：不是渲染本身慢（单测 `viz.render` 只要 12ms），而是渲染是**纯 Python
代码、需要反复持有 GIL**，与感知线程里的 PyTorch / MediaPipe 推理（会周期性
释放并抢回 GIL）互相踩踏。两者叠加后单帧渲染被拉长到 218ms。

**排除过的假设**：不是队列积压 —— 感知线程本来就是「最新帧快照」语义，
`publish/snapshot` 只保留最新一帧，从不排队。

**修复（走过一次弯路，最终方案如下）**：

第一版尝试把渲染+`imshow`+`waitKey` 整体搬到独立显示线程，用单槽邮箱丢帧。
**这个方案是错的**，实测被两次否掉：

| 实验 | 结果 |
|---|---|
| OpenCV 5.0.0：主线程 `imshow` vs 工作线程 `imshow` | **两者窗口都是全黑** |
| OpenCV 4.13：工作线程 `imshow`（主线程不泵事件） | 6 秒内投递 **1 次** |
| OpenCV 4.13：工作线程 `imshow`（主线程持续 `waitKey`）| 6 秒内投递 **0 次** |

结论：**OpenCV 的窗口只能在主线程刷新**，非 GUI 线程调用 `cv2.imshow`
会阻塞（不是丢帧，是彻底卡住）。

最终方案是**把渲染与刷新拆到两个线程**：

```
感知线程: 采集 → 推理 → [渲染 viz.render] ──> 单槽邮箱(画布)
                                              │
控制线程(主): 取画布 ──> cv2.imshow + waitKey(1)   ← 唯一能碰窗口的线程
              （非阻塞：没画布就跳过这一帧）
```

要点：
* 渲染是纯 Python、反复抢 GIL，放在**和推理同一个线程**里，
  就不会再和推理互相踩踏；控制循环每周期只花约 2ms 贴图；
* 窗口只在主线程刷新，符合 OpenCV 的硬约束；
* 画布用**单槽邮箱**交接，渲染快于上屏时覆盖旧帧（画面旧无害，控制节拍乱有害）。

**实测效果**（同一段 400 帧录像）：

| 指标 | 修复前（渲染在主循环） | 中间态（渲染独立线程，不可行） | 最终（渲染在感知线程） |
|---|---|---|---|
| 环路耗时（均/峰） | 218.3 / 282.8 ms | 44.9 / 180.6 ms | **3.9 / 13.2 ms** |
| 超时次数 | 268 / 268 | 5 | **0** |
| 控制频率 | 4.2 Hz | 20.3 Hz | **30.0 Hz**（目标 30） |
| 稳态周期均值 | 235.5 ms | 48.8 ms | **33.4 ms** |

> 附带发现（环境问题，非本项目代码）：远程机 pip 安装的
> **`opencv-contrib-python 5.0.0.93` 的 Qt 后端是坏的** ——
> `cv2.imshow` 只创建窗口、不显示内容，控制台报
> `QMetaObject::invokeMethod: No such method GuiReceiver::showImage(...)`。
> 系统 apt 的 OpenCV 4.5.4 正常。已改为 `opencv-contrib-python 4.13.0.92`
> （回退命令：`pip install opencv-contrib-python==5.0.0.93`）。
> 这个坑会让人误以为是自己的渲染代码有问题 —— 实际连主线程画个纯色方块都不显示。

### 8.2 缺陷⑧：角度滤波根本没作用到下发值（三级滤波退化为两级）

**发现方式**：逐列体检 CSV 时发现 `corr(delta_upper, mapped_joint2)` 只有 −0.125，

也就是说：**那一级滤波器对真正下发给机械臂的值毫无影响**，

**实机 A/B（400 帧录像，TRACKING 各约 165 帧，相邻帧抖动中位数）**：

### 8.3 缺陷⑨：线性 EMA 在 ±180° 附近把角度平均成 0

**发现方式**：CSV 里 `filtered_forearm` 在关键点跨过 ±180° 时**恒为 0.00**，
而 `raw_forearm` 在 ±179 之间正常摆动。

**根因**：角度是**周期量**。线性 EMA 对 +179° 与 −179° 求平均得到 **0°** ——
而这两个角的真实差只有 2°。滤波器的输出因此完全错误，
画面表现为「一跨过边界前臂就跳到 0」。

**修复**：新增 `CircularScalarFilter`，把角度转到 (cos, sin) 域分别做 EMA，
再用 `atan2` 转回角度。`AngleFilter` 改为使用它。

**验证**（同一串输入）：

| 输入序列 | 线性 EMA（旧） | 周期滤波（新） |
|---|---|---|
| raw +179 → +179 | +179.00 | **+179.00** |
| raw −179（跨边界） | **0.00** ❌ | **+180.00** ✅ |

并补了防回归测试（`test_circular_filter_*`），
断言跨边界不得塌陷到 0。

### 8.4 缺陷⑩：`joint7` 列恒为 0（本层不负责，但没人回填）

### 8.6 缺陷⑫：HUD 中文绘制每行 10.7ms（15 行吃掉 155ms）

**发现方式**：缺陷⑦修好后显示线程独立了，但实测渲染仍要 **229ms/帧**，
与单测的 12ms 相差 19 倍。逐段计时定位到 `_draw_hud` = 170ms，其余各段 < 1ms。

**根因**（分解实测）：

| 场景 | 耗时 |
|---|---|
| 15 行 CJK | **155.3 ms** |
| 15 行 ASCII | 0.76 ms |
| 1 行 CJK | 11.2 ms |
| 30 行 CJK | 285.0 ms |

纯 ASCII 快 200 倍，说明瓶颈与「字体渲染」无关。
真正原因是 `_draw_pil` 的实现：
**把整幅图 1280×720 转成 PIL → 在整幅图上画 9 遍（1 正文 + 8 方向描边）
→ 再整幅转回 OpenCV**，而这件事每行都做一次。代价与图像尺寸成正比。

**修复**：
1. 只为**这一行文字**渲染一张带 alpha 的小图，再按 alpha 叠加到大图上
   （处理的是几十×几十像素，与图像尺寸无关）；
2. 对渲染结果做缓存（HUD 里重复字符串很多），缓存上限 512 条自动清空。

**实测效果**：

| 场景 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| 1 行 CJK | 11.19 ms | 0.43 ms | 26× |
| **15 行 CJK（HUD 实际规模）** | **155.27 ms** | **1.05 ms** | **148×** |
| 30 行 CJK | 285.0 ms | 1.46 ms | 195× |

同时补了 10 项测试锁定这一性质，其中最重要的是
`test_cost_is_independent_of_image_size` —— 直接断言
「绘制代价不得随图像尺寸显著增长」，这正是旧实现的病根。

**端到端效果**：整帧渲染 `viz.render(frame, det, hand, 15行HUD)`
从 **173.7 ms 降到 7.6 ms**（其中 `_draw_hud` 从 **170.3 ms 降到 1.3 ms**）。
这正是 8.1 那条「渲染必须离开控制循环」之外的**根本解法**：
渲染便宜到 8ms 之后，它放哪儿都不再是瓶颈。

### 8.8 实时摄像头识别驱动（真实人手 → 机械臂）

并把机械臂实测的 `/joint_states` 单独录下来做交叉验证 ——

#### 8.8.1 ⚠️ 一次被我自己的探测脚本误导的「缺陷」

**先记录这个错误结论，因为它比结论本身更有价值。**

第一版探测脚本给出：

| 侧 | 肩 | 肘 | 腕 | 几何有效 |
|---|---|---|---|---|
| left | 40/40 | 30/40 | 39/40 | 30/40 |
| **right** | 23/40 | **3/40** | 39/40 | **3/40** |

据此我写下「**右肘在画面外，右臂在现有构图下不可用，必须调整机位**」，
并把它写进了报告和建议。

**这个结论是错的。** 触发怀疑的是后来一次把 `conf_threshold` 放到 0.05 的
对照探测：同一个右肘，置信度却是 **0.920**。门限不该改变模型输出 ——
说明是**探测代码**有问题，不是摄像头。

重写成「单一 provider、逐关键点显式打印、不静默跳过」后：

| 关键点 | 中位置信度 | ≥0.4 的帧 |
|---|---|---|
| left_shoulder / left_elbow / left_wrist | 0.987 / 0.774 / 0.944 | 40/40, 40/40, 40/40 |
| right_shoulder / right_elbow / right_wrist | 0.996 / **0.902** / 0.956 | 40/40, 40/40, 40/40 |

**两侧三点全部 40/40 有效，右肘 0.902 甚至高于左肘 0.774。**

再接入手部识别（这是链路里真正的差异点）：

| 侧 | 姿态腕点 conf | 手部腕点 conf | 合并后 | 几何有效(不接入手部 → 接入手部) |
|---|---|---|---|---|
| left | 0.957 | **0.998** | 0.998 | 40/40 → **40/40** |
| right | 0.901 | **0.997** | 0.997 | 40/40 → **40/40** |

手部模型定位的腕点比人体姿态更准（右 0.901→0.997），
接入手部识别**没有任何一侧被劣化**。

**教训**：探测脚本里用 `dict.get()` + `continue` 静默跳过取不到的数据，
会让「我的键名写错了」伪装成「这一侧识别不到」。
**取不到数据必须显式报错** —— 否则你会在一个不存在的问题上花掉一整天。

只在 recorder 的 26.4~27.0s 出现过一次约 0.6 秒的瞬态尖峰
（joint4 最大 1.24 rad）—— 该时段命令值始终为 0，
判断为**外部机械扰动**（机械臂快速运动时被人碰到），不是控制缺陷。

#### 8.8.4 这一节踩到的三个「数据可信度」坑

1. **`/joint_states` 不能按位置读**。
   实测该话题的 `name` 顺序是
   `[joint2, joint3, joint5, joint6, joint1, joint4, joint7, joint8]`，
   **不是 joint1..joint6**。第一版记录脚本按列序写 CSV，
   于是第 2/3 列其实是 joint3/joint5 —— 据此算出
   「joint3 出现正值、超出限位 [−2.967, 0]」，一度以为发现了严重缺陷。
   改成**按名字映射**后一切正常。凡涉及多话题对齐，必须按名字/字段对齐，
   绝不能假设顺序。

2. **跨进程时间轴必须先求偏移再谈相关性**。
   直接用各自的时间戳算相关性得到的是 ≈0（−0.08 ~ +0.13），
   看起来像「识别与机械臂完全无关」；求出 off=3.0s 后同一份数据
   变成 −0.69 ~ −0.94。**先验证对齐，再解读相关性。**

3. **探测脚本的静默 `continue` 会把「代码 bug」伪装成「硬件/环境限制」**
   （见 8.8.1）。取不到数据要报错，不要跳过。

#### 8.9.2 急停行为（数据证明真的冻结）

用 `xdotool` 在运行中按 `e`，10 秒后再按 `e` 解除，
同时独立录制 `/joint_states`。按「每 1 秒窗口内关节最大变化」统计：

| 时段 | 每秒最大变化 | 状态 |
|---|---|---|
| t=12~20s | **0.0002 ~ 0.0008 rad** | **冻结** |
| t=21~30s | 0.02 ~ 0.18 rad | 已恢复控制 |
| t=32~37.6s | **0.0000 rad** | 冻结（`q` 退出后机械臂零漂移） |

* 急停触发 → 日志 `** 软件急停触发: 手动触发 **`，机械臂**锁定在当前位置**，
  9 秒内位置变化 ≤ 0.0008 rad；
* 解除 → 日志 `急停已解除（机械臂不会自动恢复运动）`，
  **必须显式再按一次 `e`** 才恢复控制（符合设计：不自动恢复以免意外）；
* 进程退出后机械臂保持最后位置、**零漂移**，说明 `JointTrajectoryController`
  的位置保持在无人发布时依然有效。

#### 8.9.3 错误路径：坏输入必须优雅失败

用坏输入逐项测试。修复前有两处会抛裸 traceback：

| 输入 | 修复前 | 修复后 |
|---|---|---|
| 摄像头索引不存在 | `[FAIL] 无法打开帧源` | ✅ 不变 |
| 视频/图片文件不存在 | `[FAIL] 无法打开帧源` | ✅ 不变 |
| **姿态模型文件不存在** | **FileNotFoundError 堆栈** | **`[FAIL] 姿态模型文件不存在: ...`** |
| **配置非法（neutral 长度错）** | **ValueError 堆栈** | **`[FAIL] 配置加载失败: 配置错误: ...`** |

修的是「同样是用户输入错误、报错风格却不一致」——
堆栈会让人误以为程序有 bug，而去查根本不存在的代码问题。

#### 8.9.4 本节顺带修掉的测试工具缺陷

录制脚本 `rec_joint_states.py` 连踩两次，记下来避免重犯：

1. 同进程内别的节点调用 `rclpy.shutdown()` 会打断本节点的 `spin`，
   而脚本只在正常结束时写文件 → **CSV 是空的**。
   改为 `finally` 里无论如何都写盘。
2. 该环境的 `SingleThreadedExecutor` 缺 `_sigint_gc` 属性，
   `spin_once` 结束时会抛 `AttributeError`。
   定点补上该属性（而不是用 `try/except` 把真问题一起吞掉）。

### 8.10 方向直觉性修正（实测驱动的 sign）

#### 8.10.1 问题

实机反馈：**手臂弯曲方向和机械臂相反，手臂伸长时很反直觉**。

排查发现根源是「用人体肩关键点作几何枢轴」时的角度定义：
前臂角是「肘→腕」的**朝向**，而显示端是镜像的，
于是「角度变大」在观感上对应手臂往下。

#### 8.10.2 实测：用「手的高度」当判据

把手抬高在图像里等价于**腕的 y 坐标减小**（y 向下）。
所以「直觉正确」的可执行定义是：

```
corr(腕_y, 角度) < 0      # 手越高，角度越大
```

第一次采集到的相关性（`corr(腕y, 前臂角) = +0.561`）看着很确定，
**但那次腕 y 只在 427~434 之间波动（行程 7px）** ——
在几乎不动的数据上算相关性，噪声可以给出任何数值。
这是本次最容易上当的地方：**先看信号幅度，再谈相关性**。

重新采集到真实动作（腕 y 行程 **261px**）后的结果：

| 量 | 修正前 | 修正后 | 判定 |
|---|---|---|---|
| 上臂 delta | — | **−0.414** | ✅ 方向已正 |
| 前臂 delta | +0.561 | +0.224 | 改善但未归正 |
| 肘 delta | — | +0.351 | 未归正 |

#### 8.10.3 结论：这是**构型相关**的，单一 sign 无法对所有动作都正确

进一步分析发现：前臂角相对「手的高低」的相关性**符号会翻转**，
取决于手在肩的左侧还是右侧：

| 手相对肩的位置 | 手抬高时前臂角 |
|---|---|
| 手在肩**右侧** | 变大（corr > 0） |
| 手在肩**左侧** | 变小（corr < 0） |

所以不存在一个对所有动作都成立的固定符号。
本次按用户要求实现了 `mapping.*.sign`（在**做差之前**修正人体测量量），
并取 −1；上臂方向已归正，前臂/肘有改善但受构型影响。

> ⚠️ 与 `invert` 的区别（两者作用在不同环节，混在一起很难调）：
> * `sign`  修正**人体测量量本身**——「这个量变大到底代表什么」；
> * `invert` 修正**机械臂关节方向**——「关节该往哪转」。
>
> 另：`sign` 必须**在标定基准与当前测量两侧同时施加**，
> 否则差值会整体偏 2×neutral。已用
> `test_sign_does_not_bias_the_neutral_point` 锁住。

#### 8.10.4 备选方案（已实现并测试，默认未启用）

报告同时实现了另一种更彻底的思路：`geometry.pivot = "anchor"`，
把枢轴从人体肩点挪到**画面锚点**（默认底边中点）。
它的角度是「手相对画面中轴的方位」，直接可读，
且不依赖肩关键点（肩被遮挡时仍可用）。

两者的取舍已实测清楚：

| | pivot=shoulder（当前启用） | pivot=anchor |
|---|---|---|
| 肩点遮挡 | 几何+状态机双双失效 | 仍可用 |
| 方向直觉 | 构型相关，需 sign 调 | 由锚点定义，与站位强绑定 |
| 已标定参数 | 不变 | 中立值大幅偏移（实测 171°/169°），需重标 |

`anchor` 模式、12 项专项测试、以及画面上的锚点可视化都已保留，
需要时把 `geometry.pivot` 改成 `"anchor"` 即可启用。
**用户选择暂不启用**，因此默认仍是 `shoulder`。

### 8.11 「手臂伸直 → 机械臂向前伸直」的实测改造

#### 8.11.1 需求与初始判断

用户要求：**手臂伸直时，机械臂也要向前伸直**。
直觉上这应该由「肘夹角 → joint3」承担。实测把这个直觉推翻了。

#### 8.11.2 关键测量：伸直 ≠ 前伸

用 TF 正运动学在多个 (joint2, joint3) 点上量末端位置：

| joint3 | 肘夹角 | 末端 x（前后） | 末端 z（高度） |
|---|---|---|---|
| 0.0 | 89.9° | 0.124 | — |
| −1.2 | 119.1° | **0.233（该组最前）** | — |
| −2.0 | 144.1° | 0.104 | — |
| −2.9 | **169.8°（最直）** | **−0.182（收到身后）** | — |

**结论：joint3 决定「肘弯/腕高」，joint2 才决定「前伸」。**
把 joint3 推到最直，末端反而退到机身后面 ——
所以「伸直」与「前伸」在 Piper 上不是同一个自由度。

| 姿态 | joint2 | joint3 | 末端 x | 末端 z |
|---|---|---|---|---|
| 最前伸 | 2.2 | −2.0 | **0.504** | 0.194 |
| 最前伸(较高) | 2.2 | −2.5 | **0.541** | 0.330 |
| 前伸且抬高 | 1.6 | −1.6 | 0.384 | 0.340 |
| 收回 | 0.0 | −2.9 | 0.173 | 0.549 |

末端 x 可达范围 **[−0.111, +0.541]，全程约 0.65 m**。

> 本节测 FK 时踩了一个坑，值得记下来：
> 自己写的轨迹发布脚本**不能设置 `traj.header.stamp`**（保持 0 = 立即开始）。
> 设了时间戳之后 `/arm_controller` 会**静默拒绝**整条轨迹 ——
> 控制器状态仍是 `active`、不报错、不警告，机械臂**完全不动**。
> 我据此先得出「joint2/joint3 影响不了 x，行程只有 0.024 m」的错误结论，
> 差点又去改映射。参照 `piper_human_control.streaming` 的可用实现才发现差异。

#### 8.11.3 发现并修复的真实缺陷：joint3 全程钉死

回放用户真实动作的 CSV：

| 量 | 范围 | 问题 |
|---|---|---|
| `delta_elbow` | 行程 **209°** | 配置区间只有 ±65° → **全程饱和** |
| `joint3` | 最小 = 中位 = 最大 = **−1.2** | **完全没动**，钉在下限 |

即「肘夹角 → joint3」这条映射实际上**从未工作过**：
无论人怎么动，joint3 都停在 −1.2。

修复后（实测抓图运行）：

| 量 | 修复前 | 修复后 |
|---|---|---|
| joint3 行程 | **0.000**（钉死） | **1.19 rad** |
| joint2 行程 | 1.60 | **2.19 rad** |
| `corr(手抬高, joint2)` | +0.329（反向） | **−0.459 ✅ 手抬高 → 前伸** |

末端实际轨迹（离线 FK 回放 29888 个采样）：
**x 行程 0.360 m，z 行程 0.652 m**。

#### 8.11.4 仍存在的限制（如实记录）

1. **`delta_upper` 区间偏窄**：实测行程 199°，配置只有 ±60°，
   导致 joint2 有 **41% 的帧贴在上端 2.2**（已到区间边界）。
   想进一步加大前伸幅度，需要放大 `human_min/human_max`，
   或把 `neutral_joints` 的 joint2 从 0.6 往上调。
2. **z 行程仍大于 x**（0.652 vs 0.360 m）：这是 joint2/joint3 的几何耦合决定的 ——
   joint2 同时把末端抬高与前推，无法只前推不抬高。
3. **末端姿态偏「前下」**：joint3 区间上限只有 0（限位），
   达不到 FK 表里「最前伸且抬高」所需的 j3 = −2.0 ~ −2.5。
   要改善需把 `neutral_joints` 的 joint3 往负方向调并重新标定。

### 8.12 赋予腕部运动能力（joint5 / joint6 由手部姿态驱动）

#### 8.12.1 需求与改造前状态

需求：**通过手部各方向的反转、摆动，让机械臂腕关节相应变化**。

改造前：`joint5` 由「前臂方向角」驱动（实测对腕**位置**影响仅 −2.7°/rad，
依据很弱），`joint6` 直接固定在 0 —— 腕部基本没有运动能力。

#### 8.12.2 先测清腕关节到底能做什么（TF 正运动学）

| 关节 | 转角范围 | 末端位置变化 | 结论 |
|---|---|---|---|
| joint5 | ±50° | x 仅 0.108~0.125 | **纯 pitch**（末端指向在竖直平面内转） |
| joint6 | ±110° | y/z 几乎不动 | **纯 roll**（末端绕自身轴滚转） |

两个自由度天然解耦，正好对应手部的两种动作。

#### 8.12.3 新增两个人体测量量

在 `piper_human_perception.hand.compute_hand_pose` 中新增：

| 量 | 定义 | 驱动 |
|---|---|---|
| `wrist_pitch_deg` | 「手朝向（腕→中指掌指）」相对「前臂朝向（肘→腕）」的夹角 | joint5 |
| `palm_roll_deg`  | 掌横轴（index_mcp→pinky_mcp）在图像平面内的朝向 | joint6 |

> ⚠️ **单目 2D 的诚实局限**：只有「在图像平面内可观测」的转动才测得到。
> 掌心正对/背对相机时的拧转在 2D 投影里几乎不改变掌横轴方向，
> 因此 `palm_roll` 对那类转动不敏感。真要解耦需要深度相机
> （阶段七的 RGB-D 接口已预留）。

#### 8.12.4 实机验证结果（右臂）

```bash
ros2 run piper_human_retargeting retarget_demo \
  --camera 0 --side right --auto-calibrate --csv /tmp/wrist.csv
```

标定已能采到 4 个量：
`upper_arm / elbow / wrist_pitch / palm_roll`，tracking 1230/1269。

| 检查项 | 结果 |
|---|---|
| `corr(腕俯仰Δ, joint5)` | **−0.941** |
| `corr(掌滚转Δ, joint6)` | **−0.927** |
| 串扰：俯仰 → joint6 | −0.096（几乎为零）|
| 串扰：滚转 → joint5 | −0.096（几乎为零）|

**实测关节行程**（真的动了）：

| 关节 | 改造前 | 本次实测 |
|---|---|---|
| joint5 | 由前臂驱动 | **1.104 rad** |
| joint6 | **固定 0** | **2.711 rad** |

即「腕俯仰 → joint5、掌滚转 → joint6」两个自由度**独立且大幅可用**。

#### 8.12.5 过程中发现并修复的三个真实缺陷

**① 标定没有采腕部量 → 腕关节永远不动。**
`add_calibration_sample` 只吃 `ArmGeometry` 的三个手臂量，
而腕部量来自手部姿态、不在其中 → 腕部基准为空 →
映射时一直报「缺少测量量 wrist_pitch_deg」。
表现为**整条链路看起来是通的，只有腕部纹丝不动**。
修复：标定支持 `extra_measures`，demo 把 `hand_pose` 一起喂进去。

**② CSV 的关节列是硬编码的 → joint6 连列都没有。**
`to_csv_row` / `csv_header` 里写死 `("joint2","joint3","joint5")`，
joint6 加入受控集合后**日志里根本看不到它** —— 动没动无从判断。
这与 joint7、`delta_*` 是同一类「算出来了却没记录」的漏洞。
修复：覆盖全部 6 个手臂关节，未受控的按 0 写出（缺列比 0 更难发现）。
并补了 `TestAllControlledJointsInCsv` 防回归。

**③ 腕俯仰存在假跳变（单帧最大 353°）。**
关键点被误估到对侧时「手朝向 − 前臂朝向」跨过 ±180°。
实测 **9/1265 帧跳变 >90°**，会让腕关节瞬间翻转。
EMA 压不住这种跳变（它会把输出拉过去一半），
必须在 EMA **之前**拒绝：新增 `max_jump` 单帧突变门限，
超限则丢弃新值、保持上一帧输出。

> **门限必须按量分别设置**：腕俯仰的假跳变可达 353°，
> 而掌滚转本身就跨 ±180°、真实单帧变化能到 100°+。
> 我先用了一个全局 60° 门限，结果把掌滚转的真实转动
> （14°→120°）误判成跳变。最终 `wrist_pitch: 60°`、`palm_roll: 170°`。

修复后：跳变 >90° 的帧 **9/1265 → 0/1229**，最大跳变 353° → 62.6°。

#### 8.12.6 一个被这次改造放大的既有问题

腕部量是**必需测量量**：只要手部识别失败，
`used_measures()` 里的 `wrist_pitch_deg` 就取不到，
`_do_tracking` 会走「缺少测量量」分支并**返回**——
于是**整条链路（含手臂 j2/j3）一起停摆**。

实测踩到过：脚本用 `--side left`、而人是按右臂测试，
手部识别不到 → 标定只采到 2 个量 → **关节下发 0 次**。

这不是新引入的，但腕部依赖让它更容易触发。
如需「手部丢失时手臂仍继续工作」，需要把「缺失测量量」
从「整帧跳过」改成「只跳过依赖它的规则」—— 本次未改，如实记录。

### 8.13 方向驱动映射（已按用户要求回退）

#### 8.13.1 做过的尝试

用户提供视频（`arm_fwd_up.mp4`，前伸→上举→放下）并提出：
**「手臂向前伸直时机械臂也向前伸直，向上伸直时也向上伸直，
更注重腕部相对于肩部的相对角度」**。

据此实现了一版「方向驱动映射」：取人体「肩->腕」方向角作主控量，
用仿真扫描出的 FK 表（208 点，joint2×joint3 -> 方向/伸展）反解
joint2/joint3，使机械臂的臂方向**对齐**人的方向。

实现内容（**代码与 FK 表都保留在仓库里**，只是配置默认关闭）：

| 文件 | 作用 |
|---|---|
| `piper_human_retargeting/arm_direction.py` | FK 表反解 + 方向角计算 |
| `piper_human_retargeting/data/fk_table.json` | 208 点 FK 表（方向 −24°~173°，伸展 0.067~0.537 m） |
| `config/retargeting.yaml` 的 `arm_direction:` 段 | 开关、增益、neutral 方向、伸展来源 |

离线验证（用该视频回放）：人体方向行程 33.6° 映射到机械臂方向 **74.1°**，
`corr(人体方向, 机械臂方向) = +0.457`，方向确实同向跟随。

#### 8.13.2 实测暴露的问题

实机运行时出现 **`关节下发 0 次`**。逐层排查出**四个真实缺陷**，
它们都不是方向映射独有，而是被这次改造放大的既有问题：

**① `arm_direction_deg` 不在 `used_measures()` 里。**
它没有对应的映射规则（由配置直接驱动 joint2/joint3），
于是永远取不到 → 滤波不滤、标定不采、缺失检查判它不存在 →
**方向映射静默失效**（日志显示「标定完成」，但关节一次没动）。

**② 标定没有采方向量。** `ArmGeometry.as_dict()` 里没有它，
调用方必须手动补进 `extra_measures` —— 补漏了。
新增 `add_calibration_sample_for(arm, geo, hand_pose)`，
把「该补哪些量」收进 Retargeter 内部，调用方只给原始数据。

**③ 缺一个量就整帧停摆。** 手部姿态缺失（`wrist_pitch` / `thumb_offset`）
会把**整帧**判为「缺少测量量」并 return —— 手臂关节被一起停掉。
实测 **1180/1268 帧被整体跳过**。
改为「按规则跳过」：缺哪个量只跳过依赖它的规则。

**④ 标定窗口内采不到的量会让整个标定失败。**
手部姿态实测要到约 **11.6s** 才首次稳定检出，而标定窗口只有 2s ——
`finish_calibration` 因此 return False，**连手臂基准都建不起来**。
改为**部分标定**（样本足的量建基准，不足的跳过并报告），
并进一步加**基准懒建立**：某量首次可用时把当下值当作它的零点。
